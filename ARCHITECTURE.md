# Threadhunt — инфраструктура VIP-сервиса найма через Threads

> Рабочее кодовое имя — **Threadhunt** (ветка = thread, и ваши «ветки»-посты). Легко переименовать: имя живёт только в `package.json` и брендинге UI.

Документ описывает всю инфраструктуру: модель данных, сервисы, потоки данных, экраны, протокол агента и дорожную карту. Это «карта местности» — отдельные файлы скелета (`packages/*`) реализуют её по кусочкам.

---

## 1. Что это и для кого

SaaS, который автоматизирует наём через Threads:

1. **Авто-постинг** «кликабельных» постов-приманок («ищу монтажёра / дизайнера / …») — через **официальный Threads API** (легально).
2. **Авто-отбивка в директе** по кодовым словам с пере-направлением (в Telegram / на сайт / куда угодно) — через **расширение/агент у клиента** (пока DM-API закрыт).
3. **Гибкие «Поиски сотрудников»** — клиент сам создаёт поиск (название, описание, кодовые слова, шаблоны), система не привязана к «дизайнерам/монтажёрам».
4. **ИИ-генерация** постов и шаблонов отбивки из описания поиска.
5. **(Позже)** авто-отбивка через **комментарии**.

Модель — **self-serve**: клиент регистрируется сам, подключает свой Threads, заводит поиски, ставит расширение.

---

## 2. Ключевое архитектурное решение: где крутится отбивка

DM-API Threads недоступен. Есть два пути автоматизации директа, мы выбрали **второй**:

| | Сервер крутит Playwright под кукой клиента | **Расширение/агент у клиента (выбрано)** |
|---|---|---|
| Где хранятся куки | у нас (огромный риск + 2FA/капчи) | у клиента, мы не видим |
| С какого IP трафик | один наш IP на всех → бан | родной IP клиента → естественно |
| Масштаб | пул headless-браузеров, дорого | сервер раздаёт только правила, дёшево |
| Юр. риск | высокий | на клиенте, мы — инструмент |

**Следствие:** «обходная» логика из [`bot.js`](../bot.js) (поиск чатов, чтение последнего входящего, матч кодового слова, отправка ответа, дедуп по человеку) переезжает в **content-script расширения**, которое работает во вкладке `threads.com`, где клиент уже залогинен. Сервер хранит правила и лог лидов, расширение — исполнитель.

Постинг остаётся на сервере через официальный API (как в [`publisher.js`](../publisher.js)), но мультиарендно — у каждого клиента свой OAuth-токен.

## 4. Модель данных (Postgres / Prisma)

Полная схема — в [`packages/server/prisma/schema.prisma`](packages/server/prisma/schema.prisma). Главное:

- **User** — владелец аккаунта (email, план).
- **ThreadsConnection** — подключённый Threads-аккаунт клиента. Для постинга: зашифрованный `accessToken`, `threadsUserId`, `username`, `tokenExpiresAt`. Один пользователь может подключить несколько Threads-аккаунтов.
- **Device** — экземпляр расширения. `pairingToken`, `lastHeartbeat`, статус. Привязан к ThreadsConnection (с какого аккаунта он отбивает).
- **Search** (★ ядро гибкости) — «поиск сотрудника»: `title`, `description`, `status`. Заменяет захардкоженные `keywords`/`replyText` из [`config.js`](../config.js).
  - **Keyword** — кодовые слова поиска (корень + режим матча).
  - **ReplyTemplate** — тексты отбивки + `redirectTarget` (telegram/url). Несколько → A/B и ротация.
  - **PostTemplate** — посты-приманки, `source` = `manual | ai`.
  - **PublishConfig** — `enabled`, `intervalMinutes`, `maxPerDay`, `rotation`, `nextIndex` (перенос логики из [`server.js`](../server.js)).
  - **CommentRule** *(этап 3)* — правило отбивки в комментариях.
- **Lead** (★ ценный выхлоп) — входящий DM, поймавший кодовое слово: `fromUsername`, `matchedKeyword`, `repliedAt`, `replyTemplateId`, `status` (`replied | manual | failed`). Дедуп по (searchId, fromUserKey).
- **PublishedPost** — журнал публикаций (id, permalink, текст, время) — перенос `posts-log.json`.
- **AiJob** — задача ИИ-генерации.
- **Subscription** — план/биллинг (Stripe).

Мультиарендность: **у каждой строки есть `userId`**, все запросы фильтруются по текущему пользователю (row-level в коде + индексы).

## 5. Потоки данных

### 5.1 Подключение Threads (для постинга)
`Дашборд → "Подключить Threads" → OAuth (Meta) → callback → сервер сохраняет зашифрованный долгоживущий токен → BullMQ `token-refresh` продлевает раз в ~50 дней` (логика `refreshToken()` из [`publisher.js`](../publisher.js)).

### 5.2 Авто-постинг
`BullMQ repeatable job на каждый активный Search → берёт следующий PostTemplate по ротации → publisher.publishPost(token, {text, mediaUrl, mediaType}) → контейнер+публикация → пишем PublishedPost`. Лимит `maxPerDay` и интервал — из PublishConfig.

**Медиа:** пост может быть текстом, картинкой или видео (`mediaType` + публичный `mediaUrl`, как требует Threads API). Для видео контейнер кодируется не мгновенно — publisher опрашивает `status` до `FINISHED` перед публикацией (порт `waitContainerReady` из [`publisher.js`](../publisher.js)).

### 5.3 Авто-отбивка (расширение)
```
1. Клиент логинится в threads.com, открыта вкладка, расширение активно.
2. background опрашивает  GET /api/agent/tasks
      → { searches: [{ id, keywords, replyTemplates, alreadyReplied:[userKeys] }] }
3. content-script ОБХОДИТ ТРИ РАЗДЕЛА директа по порядку:
      Запросы (/messages/requests) → Скрытые (/messages/hidden) → основной (/messages/).
   Почти все холодные отклики незнакомцев Threads прячет в Запросы/Скрытые — поэтому
   они идут первыми. В каждом разделе: скан чатов, чтение последнего входящего,
   matchKeyword() (shared), пропуск тех, кто в alreadyReplied / отвечал не он.
4. перед ответом в Запросах/Скрытых — клик «Принять/Accept/Unhide» (если есть).
5. отправка ответа в DOM, затем POST /api/agent/events
      → { searchId, fromUsername, matchedKeyword, templateId, sent:true, section }
6. сервер создаёт Lead (с пометкой section), добавляет userKey в дедуп.
   heartbeat: POST /api/agent/heartbeat  (статус "агент онлайн" в дашборде).
```
Сервер — источник правды по дедупу и лидам.

**Возобновляемый обход (MV3):** в Playwright-прототипе ([`bot.js`](../bot.js)) проход — один процесс, делающий `page.goto` по разделам и чатам. В расширении любая навигация убивает content-script, поэтому обход сделан **конечным автоматом** с состоянием в `chrome.storage.session`: каждая загрузка страницы = один шаг (собрать раздел → перейти к следующему → обработать чат → следующий). Раздел `section` (requests/hidden/main) сохраняется в Lead — это аналитика «откуда приходят лиды».

**`discover-dm.js`** в прототипе — dev-разведчик, который находит точные адреса/кнопки разделов директа при смене вёрстки Threads. В Threadhunt остаётся как отладочный приём: при поломке селекторов запускаем его на прототипе и переносим новые селекторы в `content.ts`.

### 5.4 ИИ-генерация
`Дашборд "Сгенерировать посты" → POST /api/searches/:id/generate → AiJob в очередь → Claude получает title+description+тон → возвращает N вариантов постов и/или шаблонов отбивки → клиент редактирует и сохраняет как PostTemplate/ReplyTemplate`. Промпт-кэширование системного промпта (см. `packages/server/src/ai`).

## 6. Экраны дашборда (минимализм, мало кнопок)

Левый рельс с иконками, контент по центру. Тренд: чистый, тёмный по умолчанию, крупная типографика, акцентный цвет.

1. **Onboarding (3 шага)** — Подключить Threads → Поставить расширение → Создать первый поиск.
2. **Поиски** (главный экран) — карточки поисков: статус (вкл/выкл), сегодня лидов, постов опубликовано. Кнопка «+ Новый поиск».
3. **Поиск → деталь** (вкладки внутри одной страницы, без лишних кнопок):
   - *Кодовые слова* — чипы.
   - *Отбивка* — список ReplyTemplate + куда редиректим (✨ «Сгенерировать ИИ»).
   - *Посты* — PostTemplate, ротация, расписание (✨ «Сгенерировать ИИ»).
   - *Лиды* — таблица входящих, кто, какое слово, ответили ли.
4. **Лиды** (сводно по всем поискам) — мини-CRM, экспорт.
5. **Подключения** — Threads-аккаунты + статус расширения (онлайн/оффлайн, последний heartbeat).
6. **Биллинг** — план, лимиты.

Принцип «мало кнопок»: вкл/выкл — один тумблер на карточке; всё редактирование инлайн с авто-сохранением (как уже сделано в текущем дашборде — debounce + `/api/settings`).

## 8. Безопасность и риски

- **Куки клиента не хранятся** — отбивка только в расширении. Это главный смысл выбранной модели.
- **Токены постинга шифруются** (AES-GCM, ключ в KMS/env), не светятся в API-ответах.
- **Device-token** у расширения — отзываемый, скоупится одним ThreadsConnection.
- **Rate-limit отбивки** на стороне расширения (паузы между ответами, лимит в день) — анти-бан, перенос `maxChats`/задержек из [`bot.js`](../bot.js).
- **ToS Threads:** постинг легален (API); отбивка через DOM — серая зона, поэтому на стороне клиента и под его ответственностью (отразить в оферте).
- Изоляция арендаторов: каждый запрос проверяет `userId` владельца ресурса.

## 9. Дорожная карта

- **Этап 0 — Каркас (сейчас):** монорепо, схема БД, общая логика матча, мультиарендный publisher, протокол агента, скелет расширения и дашборда.
- **Этап 1 — MVP:** регистрация, OAuth Threads, создание поиска, авто-постинг по расписанию, отбивка через расширение, лог лидов.
- **Этап 2 — ИИ + полировка:** генерация постов/шаблонов, мини-CRM лидов, биллинг.
- **Этап 3 — Расширение охвата:** отбивка через **комментарии**, A/B шаблонов, аналитика, переход отбивки на DM-API когда откроется (интерфейс уже абстрагирован — меняется только исполнитель).
